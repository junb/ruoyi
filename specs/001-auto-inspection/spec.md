# Feature Specification: 服务器自动巡检

**Feature Branch**: `001-auto-inspection`
**Created**: 2026-04-05
**Status**: Draft
**Input**: User description: "通过 Prometheus 监控系统采集服务器资源指标，结合阿里云百炼智能体生成专业的巡检分析报告，替代人工巡检流程。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手动触发巡检并查看报告 (Priority: P1)

运维人员在管理界面上点击"立即巡检"按钮，系统异步采集所有服务器的 CPU、内存、磁盘指标，调用 AI 智能体生成 Markdown 格式的巡检报告。运维人员可以在报告列表中查看状态变化（待处理 → 已完成），点击查看完整的巡检报告详情。

**Why this priority**: 这是功能的核心价值——替代人工巡检，手动触发是最基本的入口，完成后即可交付最小可用产品。

**Independent Test**: 可以通过手动触发一次巡检，等待报告生成完成，查看报告内容和实例指标来完整验证。

**Acceptance Scenarios**:

1. **Given** 用户具有巡检创建权限，**When** 点击"立即巡检"按钮，**Then** 系统立即返回成功提示，报告列表中出现一条状态为"待处理"的新记录。
2. **Given** 系统正在生成巡检报告，**When** 指标采集和 AI 生成全部完成，**Then** 报告状态变为"已完成"，用户可以查看完整的 Markdown 报告和各服务器指标。
3. **Given** 系统正在生成巡检报告，**When** 指标采集或 AI 调用失败，**Then** 报告状态变为"失败"，保留错误信息，用户可以查看失败原因。

---

### User Story 2 - 报告管理与下载 (Priority: P2)

运维人员在报告列表中查看所有历史巡检报告，支持按状态筛选（待处理/已完成/失败）。可以查看报告详情（包括实例指标和 AI 生成的报告内容），下载为 Markdown 文件，以及批量删除不需要的报告。

**Why this priority**: 报告的查看、下载和管理是巡检功能的日常使用场景，但依赖 US1 的报告生成能力。

**Independent Test**: 可以通过已有报告数据验证列表查询、详情查看、文件下载和删除操作。

**Acceptance Scenarios**:

1. **Given** 系统中存在多条巡检报告，**When** 用户按状态筛选，**Then** 列表只显示对应状态的报告。
2. **Given** 一条已完成的巡检报告，**When** 用户点击下载，**Then** 浏览器下载一个 Markdown 文件，文件名包含中文报告名称。
3. **Given** 多条巡检报告，**When** 用户选择并批量删除，**Then** 报告及关联的实例指标全部被删除。

---

### User Story 3 - 失败报告重试 (Priority: P2)

运维人员对生成失败的巡检报告点击"重试"按钮，系统重新执行指标采集和 AI 报告生成流程。报告状态回到"待处理"，成功后变为"已完成"。

**Why this priority**: 重试机制保证巡检结果的可靠性，是运维场景的刚需，与 US2 并列为 P2。

**Independent Test**: 可以通过一条失败报告执行重试操作，验证状态回退和重新生成流程。

**Acceptance Scenarios**:

1. **Given** 一条失败的巡检报告，**When** 用户点击"重试"，**Then** 报告状态变为"待处理"，系统重新采集指标并生成报告。
2. **Given** 重试后生成成功，**Then** 报告状态变为"已完成"，覆盖之前的错误信息。

---

### User Story 4 - 定时自动巡检 (Priority: P3)

系统按照配置的定时规则（默认每月 1 号 9:00）自动执行巡检，生成报告。运维人员无需手动操作即可定期获得服务器巡检报告。

**Why this priority**: 自动化进一步提升效率，但核心的巡检能力已在 US1 中实现，定时只是触发方式的不同。

**Independent Test**: 可以配置一个短间隔的定时规则，等待自动触发后验证报告生成。

**Acceptance Scenarios**:

1. **Given** 定时规则已配置为每月 1 号 9:00，**When** 到达定时时间，**Then** 系统自动创建巡检报告并执行生成流程，报告触发类型标记为"定时"。
2. **Given** 定时巡检执行成功后，**When** 系统检查历史报告，**Then** 超过保留月数（默认 12 个月）的报告及关联指标被自动清理。

---

### Edge Cases

- Prometheus 服务不可用时，指标采集失败，报告状态变为"失败"，保留错误信息。
- 百炼 AI 智能体调用失败时，最多重试 3 次（指数退避 2s → 4s → 8s），全部失败后报告标记为"失败"。
- 某台服务器没有返回指标数据时，该实例的指标字段为空，不影响其他实例的采集。
- 同一时刻多次触发巡检时，每条报告独立生成，互不影响。
- 下载文件名包含中文字符时，需正确编码（RFC 5987）确保浏览器正常显示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持手动触发巡检，用户点击按钮后异步执行报告生成，立即返回。
- **FR-002**: 系统必须通过 Prometheus HTTP API 采集以下服务器指标：CPU 使用率、内存总量/可用量、磁盘各分区总量/可用量。
- **FR-003**: 系统必须将采集到的指标格式化为结构化文本，发送给百炼智能体生成 Markdown 巡检报告。
- **FR-004**: 系统必须支持按状态分页查询报告列表，支持按状态筛选和排序。
- **FR-005**: 系统必须支持查看报告详情，包括元信息、各服务器实例指标和 AI 生成的 Markdown 内容。
- **FR-006**: 系统必须支持下载报告为 Markdown 文件，文件名支持中文。
- **FR-007**: 系统必须支持批量删除报告，删除时级联删除关联的实例指标。
- **FR-008**: 系统必须支持对失败报告进行重试，重试时重新执行完整的采集和生成流程。
- **FR-009**: 系统必须支持定时自动巡检，按 cron 表达式自动触发。
- **FR-010**: 系统必须在每次成功生成报告后，自动清理超过保留月数的历史报告。
- **FR-011**: 报告状态必须包含三种：待处理（pending）、已完成（success）、失败（failed），状态变更必须立即持久化。
- **FR-012**: 系统必须记录报告生成的错误信息，便于故障排查。
- **FR-013**: 百炼 AI 调用失败时必须实施重试策略：最多 3 次，指数退避（2s → 4s → 8s）。
- **FR-014**: 权限控制必须覆盖四个权限点：查询、创建（含重试）、下载、删除。
- **FR-015**: 报告状态变更时，系统必须通过 SSE 推送实时通知前端，用户无需手动刷新即可看到状态更新。
- **FR-016**: 巡检报告页面必须作为独立的一级菜单"巡检管理"呈现，不嵌入现有系统管理或系统监控菜单下。

### Key Entities

- **巡检报告（Inspection Report）**: 一次巡检任务的完整记录，包含报告名称、日期、状态、触发方式、AI 生成的 Markdown 内容、生成耗时、错误信息等。每次巡检生成一条报告记录。
- **实例指标（Instance Metric）**: 单台服务器在某次巡检中的资源指标快照，包含 IP、CPU 使用率、内存使用情况、磁盘分区使用情况。一条报告关联多台服务器指标（一对多关系），报告删除时级联删除关联指标。
- **系统配置（字典配置）**: 通过系统字典管理的运行参数，包括 Prometheus 地址、百炼 API 密钥和应用 ID、报告保留月数等。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户点击"立即巡检"后，系统在 2 秒内返回响应，报告在后台异步生成。
- **SC-002**: 单次巡检能在 60 秒内完成所有服务器指标的采集和 AI 报告生成（假设服务器数量不超过 50 台）。
- **SC-003**: 失败报告可通过重试功能重新生成，重试成功率不低于 95%（排除 Prometheus 或 AI 服务持续不可用的情况）。
- **SC-004**: 定时巡检按时自动执行，无需人工干预，每月自动生成巡检报告。
- **SC-005**: 报告过期清理机制有效运行，历史数据不会无限增长。
- **SC-006**: 下载的 Markdown 文件名在主流浏览器（Chrome、Edge、Firefox）中正确显示中文。

## Clarifications

### Session 2026-04-05

- Q: 异步报告生成过程中，用户如何感知进度？ → A: 利用项目已有的 SSE 推送能力，实时通知报告状态变更。
- Q: 巡检报告的前端页面应放在哪个菜单位置下？ → A: 新建一级菜单"巡检管理"。

## Assumptions

- Prometheus 服务已部署并正常运行，HTTP API 可访问。
- 阿里云百炼智能体应用已创建，API Key 和 App ID 已配置到系统字典中。
- 本功能运行在 RuoYi-Vue-Plus 框架内，复用现有的用户认证、权限管理、多租户等基础设施。
- 服务器节点已安装 Node Exporter，Prometheus 已配置采集目标。
- 定时任务使用项目内置的 SnailJob 调度框架实现。
- 前端页面遵循项目现有的 Element Plus 组件风格和布局规范。
