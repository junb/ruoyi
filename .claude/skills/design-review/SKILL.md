# 设计评审 Skill

本 Skill 用于设计评审员 Agent 对项目设计文档进行系统性一致性校验，覆盖 6 大维度，输出标准化评审报告。

## 项目技术栈

- **后端：** Spring Boot 3.5.12 + Java 17 + MyBatis-Plus 3.5.16 + Sa-Token 1.44.0
- **前端：** Vue 3 + Element Plus 2.13.5 + Pinia + UnoCSS + TypeScript
- **后端路径：** `{BACKEND_DIR}/`
- **前端路径：** `{FRONTEND_DIR}/`

## 评审流程

### 第一轮评审：全面检查

对所有 6 大维度进行完整的一致性校验。

### 后续轮次：定向验证

只验证上一轮 FAIL 的项，确认修改是否到位。

### 评审上限

最多进行 **3 轮**评审。3 轮后仍有严重问题未解决，判定为评审不通过并给出最终意见。

## 一致性校验清单（6 大维度）

### 维度 1：PRD ↔ 概念设计

检查产品需求文档与概念设计之间的对应关系：

- [ ] 每个功能需求在概念设计中有对应模块
- [ ] 用户角色在权限设计中有体现
- [ ] 非功能需求（性能、安全、可用性等）有对应的技术方案
- [ ] 数据字典需求在数据库设计中有对应表

**校验方法：**
1. 逐条读取 PRD 中的功能需求列表
2. 在概念设计中查找对应的模块划分
3. 标记缺失的对应关系
4. 检查非功能需求是否有明确的技术应对策略

### 维度 2：PRD ↔ 详细设计

检查产品需求文档与详细设计之间的实现覆盖度：

- [ ] 每个功能点有对应的 API 接口
- [ ] 每个页面有对应的前端组件
- [ ] 权限要求（菜单 + 按钮）在接口和页面中都有体现
- [ ] 导入导出需求有对应实现
- [ ] 字典数据需求有对应配置

**校验方法：**
1. 从 PRD 提取所有功能点清单
2. 逐条在后端详细设计（API 列表）中查找对应接口
3. 逐条在前端详细设计（组件列表）中查找对应页面/组件
4. 检查权限点是否在前后端同时体现
5. 检查特殊需求（导入导出、字典）是否有实现方案

### 维度 3：概念设计 ↔ 详细设计

检查概念设计与详细设计之间的架构一致性：

- [ ] 接口设计符合架构规范（RESTful、`R<T>` 响应）
- [ ] 数据流设计一致（输入 → 处理 → 输出）
- [ ] 数据库表设计覆盖所有实体
- [ ] 缓存策略在详细设计中有体现
- [ ] 安全设计（权限、数据隔离）有实现

**校验方法：**
1. 对比概念设计中的数据流图与详细设计中的接口实现
2. 逐个实体检查是否有对应的数据库表
3. 检查缓存策略是否在详细设计中明确了具体实现（Redis key、过期时间等）
4. 检查安全设计方案是否在详细设计中有具体代码级别的体现

### 维度 4：UI 规范 ↔ PRD

检查 UI 设计稿与产品需求之间的覆盖度：

- [ ] 设计稿覆盖所有页面
- [ ] 交互流程与 PRD 描述一致
- [ ] 权限按钮标注完整（哪些按钮在什么角色下可见）

**校验方法：**
1. 列出 PRD 中所有页面清单
2. 逐一检查是否有对应的设计稿
3. 对比关键交互流程（新增、编辑、删除、审批等）是否与 PRD 一致
4. 检查设计稿中按钮元素是否有权限标注

### 维度 5：UI 规范 ↔ 前端详细设计

检查 UI 设计稿与前端详细设计之间的实现一致性：

- [ ] 组件设计与 Element Plus 规范一致
- [ ] 页面布局与设计稿一致
- [ ] 配色、字体、间距符合设计系统

**校验方法：**
1. 对照设计稿检查前端组件选型是否合理（如表格用 `el-table`，表单用 `el-form`）
2. 检查布局结构（栅格、弹性布局）是否与设计稿一致
3. 检查样式变量是否引用了统一的设计令牌（Design Token）

### 维度 6：前后端详细设计一致性

检查后端与前端详细设计之间的接口契约一致性：

- [ ] API 接口的 URL、方法、参数、响应格式前后端一致
- [ ] 字段名和类型前后端一致（驼峰命名）
- [ ] 分页参数格式一致
- [ ] 权限标识符一致（`{module}:{feature}:{action}`）
- [ ] 字典类型和值一致
- [ ] 枚举值前后端一致

**校验方法：**
1. 提取后端 API 列表（Controller 中的所有接口）
2. 提取前端 API 调用列表（`api/` 目录下的所有请求）
3. 逐个接口对比 URL、HTTP 方法、请求参数、响应结构
4. 对比字段命名（Java 驼峰 vs TypeScript 驼峰）
5. 对比分页参数（`pageNum`/`pageSize` vs `page`/`size` 等）
6. 对比权限标识符字符串
7. 对比字典类型编码和枚举值定义

### 严重度定义

| 级别 | 含义 | 处理要求 |
|------|------|----------|
| **严重** | 导致功能无法正常工作或数据不一致 | 必须修复，否则不通过 |
| **中等** | 影响用户体验或代码质量 | 建议修复，下轮优先验证 |
| **轻微** | 风格偏差或可优化项 | 可选优化，不阻塞通过 |

## 常见不一致问题速查表

以下是评审中高频出现的不一致问题，供快速参考：

| 问题类型 | 具体表现 | 正确做法 |
|----------|----------|----------|
| **字段命名风格不一致** | 后端 `userName`，前端 `user_name` | 统一使用驼峰命名 |
| **接口 URL 风格不一致** | `/api/user/getList`（非 RESTful） | 改为 `GET /api/user/list` |
| **权限标识符不一致** | 后端 `user:list`，前端 `system:user:query` | 统一为 `system:user:query` 格式 |
| **分页参数不一致** | 后端 `pageNum/pageSize`，前端 `page/size` | 统一使用 `pageNum/pageSize` |
| **枚举/字典值不一致** | 后端状态 0/1，前端 `active/inactive` | 统一为数值或字符串，不要混用 |
| **缺少异常场景设计** | 只设计了正常流程，未考虑边界和异常 | 补充异常码、参数校验、并发处理 |
| **字段缺失** | 响应 Vo 缺少前端需要的字段 | 补充字段或前端改为不依赖 |
| **类型不匹配** | 后端 Long，前端 Number（精度丢失风险） | 前端用 String 或后端用 String |
| **缺少分页支持** | 列表接口不分页或分页参数缺失 | 统一支持 `pageNum` + `pageSize` |
| **权限遗漏** | 接口有权限注解，前端按钮未控制可见性 | 前端同步使用 `v-hasPermi` 指令 |

## 评审注意事项

1. **逐项检查，不要跳步**：每个维度的每个检查项都要逐一验证，不能假设
2. **以文档为准**：评审依据是文档本身，不是"应该是怎样"
3. **区分严重度**：不要把所有问题都标为严重，合理分级
4. **给出可操作的修改建议**：问题描述要具体到文档和位置，修改建议要可执行
5. **保持客观**：评审是对事不对人，描述问题时不带主观评价
6. **记录评审轮次**：每次评审都要标注轮次，便于追踪改进进度
