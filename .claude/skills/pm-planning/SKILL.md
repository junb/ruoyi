# 项目经理任务规划 Skill

## 角色定位

作为项目经理，负责将PRD和技术方案转化为可执行的开发计划，跟踪任务进度，管理Bug和质量，确保项目按时高质量交付。

## 二、任务拆分策略

### 2.1 按功能模块拆分（推荐）

**适用场景：** 功能边界清晰、模块间耦合度低

**拆分方式：**
```
{功能模块A}
├── A-1 数据库设计与建表
├── A-2 后端Entity/Mapper/Service/Controller开发
├── A-3 后端业务逻辑开发
├── A-4 后端接口自测
├── A-5 前端页面开发（列表+表单）
├── A-6 前后端联调
├── A-7 功能测试
└── A-8 Bug修复

{功能模块B}
├── B-1 ~ B-8 （同上结构）
```

**优点：**
- 每个模块可独立交付
- 模块间干扰小
- 便于并行开发

**缺点：**
- 模块间公共部分可能重复开发
- 需要提前约定公共接口

### 2.2 按技术层拆分

**适用场景：** 功能模块间有强依赖，需要统一开发基础层

**拆分方式：**
```
阶段1：基础层
├── 数据库设计（所有表）
├── 公共工具类开发
├── 字典数据初始化
└── 菜单权限配置

阶段2：后端开发
├── 模块A后端开发
├── 模块B后端开发
└── 后端接口联调

阶段3：前端开发
├── 模块A前端开发
├── 模块B前端开发
└── 前后端联调

阶段4：测试
├── 功能测试
├── Bug修复
└── 回归测试
```

### 2.3 拆分粒度原则

**核心原则：** 一个任务 = 一个可独立验证的功能单元

| 原则 | 说明 | 示例 |
|------|------|------|
| **可独立完成** | 不依赖其他未完成任务 | ✅ "开发用户列表查询" ❌ "开发用户模块" |
| **可独立验证** | 完成后可以测试 | ✅ "新增用户接口" ❌ "用户相关接口" |
| **粒度适中** | 2-8小时为宜 | ✅ "开发列表+表单页面" ❌ "做一个页面" |
| **职责单一** | 一个任务只做一件事 | ✅ "开发导出接口" ❌ "开发CRUD+导出" |
| **边界清晰** | 明确输入输出 | ✅ "设计用户表结构" ❌ "准备数据库" |

**粒度参考：**
| 任务类型 | 推荐工时 | 说明 |
|----------|----------|------|
| 数据库设计 | 1-4h | 一个模块的表设计 |
| 后端接口开发 | 2-4h | 一个实体的CRUD |
| 后端业务逻辑 | 2-6h | 复杂业务处理 |
| 前端页面开发 | 2-6h | 一个页面的完整开发 |
| 前后端联调 | 1-3h | 一个功能模块的联调 |
| 功能测试 | 2-4h | 一个模块的完整测试 |
| Bug修复 | 0.5-2h | 单个或一批Bug |

### 2.4 依赖关系管理

**标准开发顺序：**
```
数据库设计 → 后端开发 → 后端自测 → 前端开发 → 联调 → 测试 → Bug修复 → 上线
```

**依赖关系标注规则：**
| 依赖类型 | 符号 | 说明 |
|----------|------|------|
| 强依赖 | `1` | 必须等任务1完成 |
| 弱依赖 | `1?` | 最好等任务1完成，但可以并行 |
| 并行 | `-` | 无依赖，可同时进行 |
| 外部依赖 | `外部:{系统名}` | 依赖外部系统 |

**并行开发策略：**
```
时间轴 →

后端：  [数据库设计] → [接口开发] → [业务逻辑] → [自测] ──→ [联调支持] → [Bug修复]
前端：               [页面开发（Mock）] → [联调] → [Bug修复]
测试：                                              [测试] → [回归测试]
```

**关键路径分析：**
- 标注关键路径上的任务（不能延期的任务）
- 关键路径上的任务预留 20% buffer
- 非关键路径任务可以适当灵活

## 三、Bug追踪模板

### 3.1 Bug记录表

```markdown
# Bug追踪：{项目/模块名称}

| # | 标题 | 优先级 | 分类 | 状态 | 提交人 | 指派 | 创建时间 | 关闭时间 | 关联任务 | 问题描述 | 复现步骤 | 修复方案 |
|---|------|--------|------|------|--------|------|----------|----------|----------|----------|----------|----------|
| 1 | {Bug标题} | P1 | 前端 | 🔧修复中 | tester | dev | 2024-01-01 | - | 任务#3 | {描述} | {步骤} | {方案} |
```

### 3.2 优先级定义

| 优先级 | 定义 | 响应时间 | 修复时限 | 示例 |
|--------|------|----------|----------|------|
| **P0** | 系统崩溃/数据丢失/核心功能完全不可用 | 15分钟 | 2小时 | 页面白屏、数据被覆盖 |
| **P1** | 核心功能异常，但有替代方案 | 1小时 | 4小时 | 提交表单报500、列表无法加载 |
| **P2** | 非核心功能异常或体验问题 | 4小时 | 1天 | 样式错乱、排序不生效 |
| **P3** | 优化建议、细节改进 | 1天 | 下个版本 | 文案调整、图标不清晰 |

### 3.3 Bug分类

| 分类 | 说明 | 常见示例 |
|------|------|----------|
| **前端** | 前端页面/交互问题 | 样式错误、交互异常、兼容性问题 |
| **后端** | 后端接口/逻辑问题 | 接口报错、数据错误、权限异常 |
| **接口** | 前后端对接问题 | 参数不匹配、响应格式不一致 |
| **配置** | 配置相关问题 | 菜单未配置、字典缺失、权限未分配 |
| **数据** | 数据相关问题 | 测试数据异常、数据不一致 |
| **性能** | 性能相关问题 | 页面加载慢、接口响应慢 |

### 3.4 Bug状态流转

```
🔍定位中 → 📋方案审核 → 🔧修复中 → ✅已修复 → 🧪验证通过 → 📦已关闭
                                    ↓
                                ⚠️强制通过（记录原因）
```

| 状态 | 说明 | 操作人 |
|------|------|--------|
| 🔍 定位中 | Bug已提交，等待定位 | 测试/开发 |
| 📋 方案审核 | 修复方案需要审核 | 技术负责人 |
| 🔧 修复中 | 正在修复 | 开发 |
| ✅ 已修复 | 修复完成，等待验证 | 开发 |
| ⚠️ 强制通过 | 因时间原因暂不修复 | 项目经理 |
| 📦 已关闭 | 验证通过，Bug关闭 | 测试 |

### 4.3 风险预警

**风险预警级别：**

| 级别 | 触发条件 | 处理方式 |
|------|----------|----------|
| 🔴 红色预警 | 进度偏差 > 30% 或 P0 Bug 未修复 | 立即开会，调整计划 |
| 🟡 黄色预警 | 进度偏差 15%-30% 或 P1 Bug 超时 | 评估影响，调整资源 |
| 🟢 正常 | 进度偏差 < 15% | 正常跟踪 |

**常见风险信号：**
- 任务实际工时持续超过预估工时
- 频繁出现 P0/P1 Bug
- 需求频繁变更
- 关键人员请假或离职
- 外部依赖延期

## 五、RuoYi项目特有的规划要点

### 5.3 数据库脚本管理

**SQL脚本命名规范：**
```
sql/
├── {module}/
│   ├── V1.0.0__create_table_{table1}.sql
│   ├── V1.0.0__create_table_{table2}.sql
│   ├── V1.0.0__init_dict_{module}.sql
│   ├── V1.0.0__init_menu_{module}.sql
│   └── V1.0.1__alter_table_{table1}_add_column.sql
```

**脚本管理原则：**
- 每个版本独立目录
- 建表、字典、菜单分开管理
- 变更脚本使用增量格式
- 所有脚本纳入版本控制

### 5.4 字典数据同步

**字典同步检查：**
- [ ] 后端 SQL 脚本中包含字典初始化数据
- [ ] 前端页面正确引用字典（useDict）
- [ ] 字典变更时同步更新前后端

### 5.5 RuoYi开发流程参考

```
1. 需求评审
```
