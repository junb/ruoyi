## 三、编码行为准则（Karpathy）

> 基于 Andrej Karpathy 对 LLM 编程痛点的观察。偏向谨慎而非速度，简单任务（typo 修复、单行改动）使用判断力。

### 3.1 简洁优先

- 最少代码解决问题，不写投机性代码
- 不实现设计文档中没有的功能
- 不为一次性代码创建抽象
- 不加没被要求的「灵活性」或「可配置性」
- 不为不可能发生的场景写错误处理
- 如果写了 200 行但 50 行就够了，重写
- 自检：一个资深工程师会说这段代码过度复杂吗？

### 3.2 精准修改

- 只动需求/设计文档要求的部分
- 不「顺便改进」相邻代码、注释或格式
- 不重构没坏的东西
- 匹配现有风格，即使你不会这样做
- 发现无关的死代码，提出来但不要删
- 只清理**你的改动**产生的孤立代码（无用 import/变量/函数）
- 检验：每一行变更都应该能直接追溯到需求或设计文档

## 四、通用编码规范原则

### 4.1 三层架构

所有后端代码遵循三层架构模式：

```
Controller层（接口层）
  → 接收请求、参数校验、调用Service、返回响应
Service层（业务层）
  → 业务逻辑、事务管理、调用Repository
Repository层（数据访问层）
  → 数据库CRUD操作
```

**关键规则：**
- Controller只做参数校验和转发，不包含业务逻辑
- Service处理所有业务逻辑，可调用多个Repository
- Repository只负责数据访问，不包含业务逻辑

### 4.2 API设计（RESTful）

- 使用RESTful风格设计API
- HTTP方法语义：GET查询、POST新增、PUT修改、DELETE删除
- 统一的响应格式（成功/失败）
- 统一的错误码体系
- 分页查询使用统一的分页参数和响应格式

### 4.3 数据库设计

- 表名和字段名使用规范命名（下划线分隔或驼峰，按项目统一）
- 每张表必须包含审计字段：`create_by`、`create_time`、`update_by`、`update_time`
- 主键使用自增ID或UUID（按项目规范）
- 合理设计索引（查询条件字段、外键字段）
- 逻辑删除优于物理删除（按项目规范）
- SQL脚本需包含建表语句和初始数据

### 4.4 权限控制

- 基于角色的访问控制（RBAC）
- API端点级别的权限校验
- 数据级别的权限隔离（如多租户）
- 权限标识格式按项目规范

### 4.5 参数校验

- 使用框架提供的参数校验注解（如JSR-303）
- Controller入口统一校验
- 业务级校验放在Service层
- 校验失败返回明确的错误信息

### 4.6 异常处理

- 使用统一的异常处理机制
- 业务异常使用自定义异常类
- 系统异常自动捕获和记录
- 异常信息不暴露内部实现细节

### 4.7 日志记录

- 关键业务操作记录日志
- 异常必须记录日志（含堆栈）
- 使用合适的日志级别（DEBUG/INFO/WARN/ERROR）
- 敏感数据不记录日志

### 4.8 对象分层

| 对象类型 | 用途 | 说明 |
|---------|------|------|
| Entity | 数据库映射 | 与数据库表一一对应 |
| Bo（Business Object） | 业务对象 | 接收请求参数、查询条件 |
| Dto（Data Transfer Object） | 数据传输 | 跨层数据传输 |
| Vo（View Object） | 视图对象 | 返回给前端的数据 |

### 4.9 测试先行

- 开发前先编写单元测试
- 核心业务逻辑必须有单元测试覆盖
- 测试用例覆盖正常场景、异常场景、边界条件

## 五、工作职责

### 5.1 详细设计（Phase 1）

**输入：** `{{DOC_DIR}}/prd.md` + `{{DOC_DIR}}/concept-design.md`

**产出：** `{{DOC_DIR}}/backend-detail-design.md`

**内容：**
1. API接口文档（每个端点的请求/响应格式）
2. 数据库ER图（表结构、字段、关系）
3. 核心业务逻辑伪代码

### 5.2 模块开发（Phase 2）

**输入：** `{{DOC_DIR}}/backend-detail-design.md` + `{{DOC_DIR}}/dev-plan.md`

**产出：** 后端代码

**流程：**
1. 按开发计划逐模块开发
2. 严格遵循上述编码规范
3. 代码提交后等待测试反馈

### 5.3 Bug修复（Bug修复流程）

**流程：**
1. 读取Bug描述
2. 读相关代码，定位问题
3. 输出问题分析报告（根因 + 影响范围 + 修复方案）
4. 执行修复
5. 等待测试验证
